## 二、Phase 1：公开面收尾（本周）

- [ ] 仓库简介与 Topics 填好
- [ ] `README.md` 链接全量核对一遍（不留死链）
- [ ] 首版 tag `v0.9.32`（只打 tag，不发二进制）
- [ ] 公开一份"能复现构建的最小验证"说明：macOS 26 + Swift 6.2 上 `./build.sh && ./test.sh`

## 三、Phase 2：样本管线（V0.9.33）

小版本，只做两件事：**加导出、加脱敏**。不改判定逻辑、不动规则语义。

- [ ] `xue.sample/v1` 导出器（见 [SAMPLES.md](SAMPLES.md)）
- [ ] 导出前强制脱敏：路径模式化、数值分桶、`raw_paths` 恒为 false
- [ ] 导出包 `manifest.json` 带 sha256，可校验完整性
- [ ] 不联网：导出只在本地生成 zip，上传由用户自己决定

**验收线**：任意一份导出样本，用 `grep` 搜不到本机用户名、真实文件名、软件序列号。

## 四、Phase 3：规则贡献通道

- [ ] 规则 PR 的自动校验（schema + id 唯一 + reason 非空）
- [ ] 规则试扫脚本对贡献者开放（`ReleaseSim` 的只读模式）
- [ ] 建立"规则来源等级"：`official` / `vendor` / `community`，社区来源默认只做 `review`
- [ ] 每季度一次规则复核，过期条目降级而不是直接删

## 五、Phase 4：镜像与分发边界

- [ ] Gitee 只读镜像（国内访问），issue / PR 仍然只在 GitHub
- [ ] 同步策略：打 tag 后手动镜像，不做自动双推
- [ ] 持续只发源码：未签名 `.app` 不作为发布物（否则等于让用户去关 Gatekeeper）

## 六、Phase 5：V1.0 前的判断点

90 天后回头看三件事，再决定 V1 范围：

1. 样本量够不够支撑规则扩充（不足就先停，别硬做社区样本）
2. 误删率是否为 0（有任何一例真实误删，先修而不是加功能）
3. 维护成本是否可持续（一个人维护的仓库，规则库别超过 200 条）

## 七、明确不做

| 不做 | 原因 |
|---|---|
| 云端账号 / 云规则库 / 云样本上传 | 一个清理工具不该有你的数据 |
| 遥测、埋点、崩溃上报 | 同上 |
| 后台常驻守护进程替你删东西 | 不可确认的删除就是风险 |
| 自动更新通道 | 当前只发源码，没有可更新的二进制 |
| Windows / Linux 移植 | 全部逻辑建立在 macOS 的 TCC、废纸篓、App 包结构上 |
| 付费版 / 授权码 | GPL-3.0 整仓开源，不做双许可证商业版 |
| 未签名二进制分发 | 用户要关 Gatekeeper 才能装，等于教人降低安全性 |

## 八、版本号规则

- 阶段内只递增补丁位：`0.9.x`
- 阶段出门才升次版本：`1.0.0`
- 规则库 `version` 与 App 版本**解耦**，可单独前进，但必须与 `CHANGELOG.md` 对齐
